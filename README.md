# Pimcore Dev Runtime

Remote development environment for Aggrosoft Pimcore bundles.

The runtime uses the real `aggrosoft/pimcore-app` repository as the host application and checks development bundles out separately below `/var/www/bundles`. The host application's Composer-installed Aggrosoft packages are replaced with symlinks to those editable checkouts.

The result is a persistent remote Pimcore instance that can be opened directly through VS Code Remote SSH and used by developers or coding agents for unit, integration and UI testing.

## Workspace

```text
/var/www/
├── AGENTS.md
├── html/                         # aggrosoft/pimcore-app
├── bundles/
│   ├── pimcore-data-bundle/
│   ├── pimcore-catalog-sources-bundle/
│   ├── pimcore-shirtnetwork-bundle/
│   ├── pimcore-shopware-bundle/
│   ├── pimcore-warexo-bundle/
│   └── pimcore-agent-bundle/
└── data -> /var/data
```

`/var/www`, the database, OpenSearch data, RabbitMQ data and `/var/data` are backed by named volumes and survive normal container recreation.

## Runtime image

GitHub Actions publishes:

```text
ghcr.io/aggrosoft/pimcore-dev-runtime:main
```

The image extends the same Pimcore 5.x/PHP 8.5 max image family used by the live application and adds only development plumbing:

- `developer` user for VS Code/SSHPiper
- GitHub App Git authentication
- Chromium for browser smoke tests
- netcat for VS Code Remote SSH forwarding
- runtime scripts for workspace setup and bundle linking

Pimcore itself is not baked into the image. The configured host application repository is cloned into the persistent workspace.

## Coolify

Use `compose.coolify.example.yaml` as the Coolify Compose template.

The template starts:

- MariaDB 10.11
- Redis
- RabbitMQ
- OpenSearch 2
- Mercure
- a one-shot Pimcore setup service
- PHP-FPM
- Pimcore Supervisord workers
- nginx

The setup service is idempotent. Existing Git working copies are never pulled, reset or deleted automatically.

## GitHub and SSH

The development instances use the same project-shared GitHub App and SSHPiper key setup as the Shopware development template.

Project-shared values:

```text
GITHUB_APP_CLIENT_ID
GITHUB_APP_INSTALLATION_ID
GITHUB_APP_PRIVATE_KEY
SSH_AUTHORIZED_KEYS_B64
```

Reference them from the Coolify resource:

```text
GITHUB_APP_CLIENT_ID={{project.GITHUB_APP_CLIENT_ID}}
GITHUB_APP_INSTALLATION_ID={{project.GITHUB_APP_INSTALLATION_ID}}
GITHUB_APP_PRIVATE_KEY={{project.GITHUB_APP_PRIVATE_KEY}}
SSH_AUTHORIZED_KEYS_B64={{project.SSH_AUTHORIZED_KEYS_B64}}
```

Keep the GitHub private key multiline.

SSH access is key-only and uses SSHPiper's Docker exec mode. No SSH daemon is required inside the Pimcore container.

## Pimcore installation

The host repository defaults to:

```text
aggrosoft/pimcore-app
```

Override it with `PIMCORE_APP_REPOSITORY` only when necessary.

A fresh database requires `PIMCORE_PRODUCT_KEY`. The remaining application infrastructure values are generated by Coolify or supplied through environment variables.

The runtime deliberately takes Pimcore and package versions from `pimcore-app/composer.lock`; there is no separate `PIMCORE_VERSION` setting.

## Development bundles

When `DEV_BUNDLES` is empty, these repositories are checked out:

```text
aggrosoft/pimcore-data-bundle
aggrosoft/pimcore-catalog-sources-bundle
aggrosoft/pimcore-shirtnetwork-bundle
aggrosoft/pimcore-shopware-bundle
aggrosoft/pimcore-warexo-bundle
aggrosoft/pimcore-agent-bundle
```

`DEV_BUNDLES` can override that list using one `owner/repo` per line.

After every host application `composer install` or `composer update`, restore the editable links with:

```bash
pimcore-dev-link-bundles
```

Bundle development dependencies are intentionally not installed six times during every environment bootstrap. Before testing a bundle, run from its repository:

```bash
pimcore-dev-bundle-deps
composer quality
```

The helper installs the bundle's own `require-dev` packages. If the library does not track a `composer.lock`, a lock file generated by Composer is removed again automatically.

## Integration credentials

Use the same environment variable names as production, but point them exclusively at development/test accounts and endpoints.

Supported pass-through variables currently mirror the live application:

```text
WAREXO_BASE_URL
WAREXO_USERNAME
WAREXO_PASSWORD
WAREXO_CLIENT_ID

SHOPWARE_BASE_URL
SHOPWARE_CLIENT_ID
SHOPWARE_CLIENT_SECRET

SHIRTNETWORK_USERNAME
SHIRTNETWORK_PASSWORD
SHIRTNETWORK_SKU_SCHEME

NORTY_HUB_URL
NORTY_HUB_USER
NORTY_HUB_PASS

BEECHFIELD_HUB_URL
BEECHFIELD_HUB_USER
BEECHFIELD_HUB_PASS

MEDIA_AI_OPENAI_API_KEY
```

S3 variables are also passed through when an explicit development bucket is required. Leave them empty otherwise.

There are no production fallbacks in the runtime. Missing integration values simply remain empty.

Values that are shared by all Pimcore development instances can be stored as Coolify project variables and referenced by each resource.

## CSV and source files

Files used for imports are deliberately simple.

The persistent directory:

```text
/var/data
```

is available in the VS Code workspace as:

```text
/var/www/data
```

CSV exports and other source files can therefore be copied into the environment manually through VS Code/SSH without adding an upload service to the template.

Example:

```text
/var/data/
├── lshop/
├── daiber/
├── atlantis/
└── tmp/
```

## Git behavior

The runtime only clones missing repositories.

It never automatically:

- pulls
- resets
- cleans
- stashes
- checks out another branch
- commits
- pushes

This protects work in persistent development instances.

The default Git identity is:

```text
Aggrosoft Dev Server <dev-server@aggrosoft.de>
```

Override it with `GIT_USER_NAME` and `GIT_USER_EMAIL` if required.
